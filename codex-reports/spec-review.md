# DeepSlime SPEC v0.1 评审

## 结论

方向成立，但当前 SPEC 还不足以直接进入完整 P0 编码。任务中心、原始记录不删、事实/草稿隔离和可见溯源是正确约束；阻塞项是写入信任边界、崩溃与并发一致性、事实晋升规则、任务身份/召回契约。建议先把 P0 收缩成“单机、单写者、手动锚定、可审计接续”的闭环。

## 架构漏洞

### Critical

1. **来源字段可自报，不能构成安全机制。** 任意 MCP 客户端都可填写 `agent`、`session_id`、`confidence`、`layer=fact`；SPEC 又允许任何 agent 读写。恶意或失控客户端可伪造高置信事实，污染简历场景。应由服务端从已认证连接生成 provenance，客户端只提交内容；`fact` 需明确的证据或人工晋升规则。
2. **文件写入没有一致性模型。** `task.record`、`checkpoint`、`close` 会同时改日志、状态、元数据和索引，但没有单写者约束、锁、原子替换、幂等键、崩溃恢复或索引重建协议。重复调用、进程中断和多 agent 并发会造成丢写、部分关闭或索引与源文件分叉。

### Major

1. **任务身份与边界未定义。** `open(name|id)` 未说明同名解析、创建/打开语义、当前任务归属及 `reattach` 在多客户端下指向谁；“相似任务苏醒”也没有阈值、拒绝和解释契约，容易串任务。
2. **schema 无版本、无演进机制。** 风险登记承诺版本化，5.4 却没有 `schema_version`；也缺少未知字段、迁移失败和旧数据读取策略。
3. **事实模型过薄。** `fact|draft` 是调用方给出的标签，不含证据、事实主体、有效时间、失效时间、冲突关系和人工确认状态，无法可靠落实“简历只读事实层”及“保留矛盾双方”。
4. **`payload_ref` 的边界不清。** 未限定只能是任务目录内的相对路径，也无内容哈希、MIME/大小和缺失文件行为，存在目录穿越、引用漂移及产物被替换后仍沿用旧结论的风险。
5. **授权粒度与数据布局不匹配。** `source_scope` 只是条目字段；没有主体、权限检查点、默认拒绝和降权规则。个人 vault 中预埋 `team|company` 会让 P2 权限模型倒灌 P0。
6. **“原始日志”定义矛盾。** 5.2 称 log 为原始且不删，2.5 又称片段是压缩事件摘要；没有明确原始对话/外部文件究竟是否保存、保存在哪里、摘要如何反查原证据。
7. **可观测性不足。** 没有 append/召回/过滤/确认的审计事件，也没有评测数据采集方法，7 章指标无法复现。

### Minor

1. `task.checkpoint` 与 `task.handoff` 都更新接续简报，职责重叠，容易产生两个真相源。
2. `type` 同时含 `fact`，`layer` 又区分 `fact`，语义重复且可能出现 `type=question, layer=fact` 等不清晰组合。
3. `agent` 是封闭枚举，与“任何 agent”及插件生态冲突；更适合稳定客户端 ID 加可显示名称。
4. `timestamp` 只写 ISO8601，未规定 UTC、服务端生成和排序相同时的处理。
5. 目录说明称 markdown/JSON 可由 Git diff，但未定义秘密扫描、忽略索引及敏感数据误提交防护。

## 与同类项目的差距

| 项目 | 已有能力 | DeepSlime 的差距 |
|---|---|---|
| Mem0 | 自托管库/服务、可配置 LLM/嵌入/向量库/重排器、历史存储、审计日志与评测路径；检索支持实体关联。 | 缺少可执行的写入提取/更新策略、过滤与重排契约、历史/删除 API、评测基线、运维与提供商抽象。DeepSlime 的优势应聚焦“任务生命周期 + 人可审计产物”，不宜泛称通用 agent memory。 |
| Zep / Graphiti | 把聊天、文本、JSON 组织为时间知识图谱；事实带有效/失效时间，保留历史，并提供跨 thread 上下文与多种 context primitive。 | 缺少时间有效性、实体解析、事实失效/冲突表达、episode 到事实的可追踪关系，以及稳定的 context 组装契约。仅有时间戳不能覆盖“几年后改简历”的事实变化。 |
| basic-memory | 已实现本地优先、Markdown 事实源、MCP、文件监听、全文/语义/图检索、schema 校验、稳定 memory URL、Obsidian/编辑器兼容及本地/云同步。 | 5.1 的大部分基础设施并不新颖，且当前 SPEC 在索引重建、文件监听、稳定引用、schema 验证、图关系和同步冲突方面明显落后。差异化必须由“任务 open/checkpoint/close/reattach 契约”和事实安全证明，而不是 Markdown + MCP + Obsidian。 |

对比依据：Mem0 [Open Source Overview](https://docs.mem0.ai/open-source/overview)；Zep [Key Concepts](https://help.getzep.com/concepts) 与 [Context Types](https://help.getzep.com/context-types)；basic-memory [Technical Information](https://docs.basicmemory.com/reference/technical-information) 与 [MCP Tools Reference](https://docs.basicmemory.com/reference/mcp-tools-reference)。

## 最值得质疑的 5 个设计决策

1. **把 Obsidian 图谱视图当“任务菌落地图”。** 普通双链图表达的是文档关系，不天然表达任务实例、时间、状态和来源；若为适配视觉效果而制造链接，会反向污染数据模型。P0 应把 Obsidian 视为可选文件浏览器。
2. **以任务作为唯一主键。** 周报适合，个人经历、公司、技能和证据常跨多个任务；全塞进任务会复制事实并制造冲突。任务应是工作上下文，不应垄断事实身份。
3. **`open` 自动召回相似任务。** 冷启动时缺乏足够意图，自动加载最容易误召回和泄露无关上下文；这与 `<5%` 误加载率及“可见加载”要求冲突。P0 应只建议候选，用户确认后展开。
4. **用 `fact|draft` 二值标签保护简历。** “事实”不是作者声明，而是带证据、时间和审核状态的主张。二值标签会制造虚假的安全感，应至少引入 `claim -> evidence -> confirmation` 流程，或 P0 仅允许用户确认后晋升。
5. **P0 同时承诺场景一和跨年简历场景。** 场景二实际需要异构导入、去重、时态冲突、覆盖缺口和高召回评测，远超 2–4 周插件闭环；把它作为功能范围会迫使团队过早建设通用知识系统。

## MVP（场景一 + 二）裁剪建议

### 保留

- 单机、单用户、单守护进程/单写者；只支持 DSH Cordis 一个入口。
- 手动 `open`、`record`、`checkpoint`、`close` 四步闭环；`open` 只按明确 ID/名称，不自动打开相似任务。
- append-only JSON 日志、一个 `state.md` 投影、原子替换与启动时重建；先做关键词/元数据检索。
- 主动投喂本地文件；保存相对路径、内容哈希和用户确认的事实条目。
- 场景一做端到端主验收：跨两次会话恢复周报状态，展示每条来源。
- 场景二只做受控验收夹具：用户手动导入旧简历/周报，查询只返回已确认事实，并明确展示未接入年份。

### 推迟到 P1

- 向量索引、相似任务自动召回、`reattach` 的意图检测、自动捕获和任务原型学习。
- Obsidian 自定义溯源插件、图谱可视化；P0 直接查看 Markdown/JSON 即可。
- 程序记忆/skills、团队与公司 scope、多设备同步、SaaS、跨 agent 全覆盖。
- 自动压缩和独立 `handoff` 工具；P0 让 `checkpoint` 维护唯一的 `state.md`，`close` 只改生命周期状态。
- 简历的全量历史连接器和自动事实抽取；在事实晋升、冲突与缺口模型通过评测后再扩展。

### P0 验收门

1. 进程在任一写入阶段被终止后，重启不丢已确认日志，且可重建 `state.md`/索引。
2. 同一幂等键重复 `record` 不产生重复条目；非法 `payload_ref` 被拒绝。
3. 新会话用明确 task ID 恢复后，用户能从每条摘要定位到原始来源。
4. 简历查询的结果全部来自用户确认的事实；未接入时间段明确列为缺口，而非“无经历”。
